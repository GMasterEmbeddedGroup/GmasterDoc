# 通信协议

本文结合《RoboMaster 2026 机甲大师高校系列赛通信协议 V2.0.0（20260626）》整理，包含机器人侧串口协议和自定义客户端协议，完整 PDF 附在文末。本文引用的页码为文档印刷页码，PDF 阅读器页码需加 1。

RMUC 与 RMUL 共用的兵种、机制和场地道具适用本协议；仅属于某一赛项的条目不自动适用于另一赛项。

- **串口部分**：整理帧格式、完整命令码索引、关键字段及交互约束；逐位定义和完整结构体请按页码查阅文末原文。

## 1 串口协议

### 1.1 串口协议格式

来源：原文第 4～5 页，表 1-1～1-4。串口统一使用 **8 位数据位、1 位停止位、无硬件流控、无校验位（8N1）**。

| 物理接口 | 波特率 |
| --- | --- |
| 电源管理模块 ↔ 机器人 | 115200 |
| 自定义控制器 ↔ 选手端 | 115200 |
| 图传发送端 ↔ 机器人 | 921600 |

| 帧组成 | 长度 | 说明 |
| --- | --- | --- |
| `frame_header` | 5 byte | 帧头，含 CRC8 |
| `cmd_id` | 2 byte | 命令码 |
| `data` | n byte | 命令对应的数据段 |
| `frame_tail` | 2 byte | CRC16，整包校验 |

完整帧长为 **n + 9 byte**，`data_length` 仅表示 `data` 长度。

| 帧头字段 | 字节偏移 | 长度 | 说明 |
| --- | --- | --- | --- |
| `SOF` | 0 | 1 | 固定为 `0xA5` |
| `data_length` | 1 | 2 | 数据段长度 |
| `seq` | 3 | 1 | 包序号 |
| `CRC8` | 4 | 1 | 帧头校验 |

三类数据链路：

| 链路 | 数据路径 / 接口 |
| --- | --- |
| 常规链路 | 裁判系统服务器与主控模块转发，经电源管理模块的 User 串口收发 |
| 图传链路 | 选手端与图传模块转发，经图传发送端串口与机器人交互 |
| 雷达无线链路 | 裁判系统信号发射源发送电磁波，由雷达接收并解析 |

原文给出的参考数据：正常情况下延迟约 130 ms、丢包率小于 1%；网络较差时延迟约 200 ms、丢包率约 3%。这些是参考测量值，并非实时性保证。

**实现建议**：接收端先寻找 `0xA5`，收齐帧头并检查 CRC8，再根据长度收齐完整帧并检查 CRC16，最后按命令码解析；同时处理半包、粘包、超长长度和校验失败后的重新同步。CRC 参数见附录一。

#### 0x0301 机器人交互与 UI

来源：原文第 23～31 页。数据段前 6 字节依次为 `uint16_t data_cmd_id`、`uint16_t sender_id`、`uint16_t receiver_id`，之后是最多 112 字节内容。完整包不超过 127 字节，**所有子内容共享 30 Hz 上行频率上限**。

每 1000 ms，英雄、工程、步兵、空中机器人和飞镖可接收数据上限为 3720 字节，雷达和哨兵为 5120 字节。机器人间仅限己方且需满足规则允许的接收者范围；发送到选手端时，除雷达外只能发送到自身对应的选手端，雷达可发送到任意己方选手端。

| 子内容 ID | 内容长度（不含 6 字节交互头） | 用途 |
| --- | --- | --- |
| `0x0200`～`0x02FF` | 最大 112 | 机器人之间通信 |
| `0x0100` | 2 | 删除图层：操作类型与图层号 |
| `0x0101` | 15 | 绘制 1 个图形 |
| `0x0102` | 30 | 绘制 2 个图形 |
| `0x0103` | 75 | 绘制 5 个图形 |
| `0x0104` | 105 | 绘制 7 个图形 |
| `0x0110` | 45 | 15 字节字符配置与 30 字节字符数据 |
| `0x0120` | 4 | 哨兵自主决策指令 |
| `0x0121` | 8 | 雷达自主决策指令 |

UI 单个图形由 3 字节图形名和三组 4 字节配置组成。配置包含操作、图形类型、图层、颜色、线宽、起点及类型相关参数。图层为 0～9；图形名用于修改和删除索引。图形坐标原点在屏幕左下角，右上角为 `(1920, 1080)`；角度 0° 为 12 点钟方向，顺时针绘制。浮点显示值为所传 32 位整型数除以 1000。具体位宽和不同图形参数见表 1-27～1-32。

`0x0120` 的 32 位哨兵指令：

| 位 | 含义 |
| --- | --- |
| bit 0 | 确认复活 |
| bit 1 | 确认兑换立即复活 |
| bit 2～12 | 在补血点兑换的累计发弹量请求，开局为 0，必须单调递增 |
| bit 13～16 | 远程兑换发弹量请求次数，开局为 0，每次递增 1 |
| bit 17～20 | 远程兑换血量请求次数，开局为 0，每次递增 1 |
| bit 21～23 | 姿态：1/2/3 为进攻/防御/移动，4/5/6 为对应强化姿态，默认 3 |
| bit 24 | 确认使能量机关进入正在激活状态 |
| bit 25～31 | 保留 |

服务器从低位到高位依次处理，遇到不能处理的指令会停止处理本组后续指令。

`0x0121` 包含 1 字节双倍易伤请求计数、1 字节密钥指令类型和 6 字节密钥。请求计数从 0 开始、每次递增 1；密钥指令 1 为更新己方密钥，2 为提交破解的对方密钥。只有开局或对方破解成功导致己方加密等级提高时可修改己方密钥；提交验证密钥后 10 秒内再次更新无效。

### 1.3 小地图交互数据

来源：原文第 32～36 页。

- **`0x0303` 下发标记**：云台手两次操作间隔至少 0.5 s；半自动机器人对应操作手两次操作间隔至少 3 s。字段为目标 x/y（m）、键盘键值、对方机器人 ID、信息来源 ID。发送目标 ID 时坐标为 0，发送坐标时目标 ID 为 0。
- **重复发送机制**：一次触发后额外按 100 ms 间隔发送 4 次，共 5 次；之后以 1 Hz 持续发送最近一次内容，直到下一次触发。接收端应考虑重复指令处理。
- **`0x0305` 雷达坐标**：按对方 1/2/3/4/6/7 号、己方 1/2/3/4/6/7 号顺序发送，每台机器人 x/y 各 2 字节，单位 cm，共 48 字节。x、y 都为 0 表示未发送该机器人坐标，越界坐标显示在边缘。
- **`0x0307` 路径**：意图 1=攻击、2=防守、3=移动；起点 x/y 为分米，后跟各 49 个 `int8_t` 增量和发送者 ID。串口表说明增量相对上一个点计算，共形成 49 个新点。小地图左下角为原点，向右为 X 正方向，向上为 Y 正方向。
- **`0x0308` 自定义消息**：发送者和接收者 ID 各 2 字节，字符区 30 字节，采用 UTF-16，支持中文，需注意编码字节序。

来源：原文第 7～8、37～38 页。

| 命令码 | 最大数据长度 | 方向 | 频率上限 | 客户端对应消息 |
| --- | --- | --- | --- | --- |
| `0x0302` | 30 byte | 自定义控制器 → 选手端图传连接的机器人 | 30 Hz | — |
| `0x0309` | 30 byte | 机器人 → 对应选手端连接的自定义控制器 | 10 Hz | — |
| `0x0310` | 300 byte | 机器人 → 图传链路 → 自定义客户端 | 50 Hz | `CustomByteBlock` |

### 1.5 非链路数据

来源：原文第 38～39 页。`0x0306` 用于自定义控制器模拟键鼠操作选手端，数据长 8 byte，发送频率上限 30 Hz。

| 字节偏移 | 长度 | 内容 |
| --- | --- | --- |
| 0 | 2 | 两个通用键值，各占 1 字节，支持 2 键无冲 |
| 2 | 2 | bit 0～11：鼠标 X；bit 12～15：左键状态 |
| 4 | 2 | bit 0～11：鼠标 Y；bit 12～15：右键状态 |
| 6 | 2 | 保留 |

这里使用绝对像素坐标，**左上角为 `(0, 0)`**，与 UI 绘图的原点不同。鼠标状态 1 为按下，其余为未按下。一次移动点击依次发送“目标位置未按下 → 同位置按下 → 同位置未按下”。无新按键信息时保持上一帧按下状态；鼠标信息仅在鼠标图标出现时响应。

### 1.6 雷达无线链路数据

来源：原文第 39～43 页，信号发射源 → 雷达，以下消息均以 10 Hz 持续发送。

| 命令码 | 长度 | 内容与排列 |
| --- | --- | --- |
| `0x0A01` | 24 | 对方 1/2/3/4/6/7 号位置，x/y 各 2 字节，单位 cm |
| `0x0A02` | 12 | 对方 1/2/3/4 号血量、2 字节保留位、7 号血量，各项 2 字节 |
| `0x0A03` | 10 | 对方 1/3/4/6/7 号允许发弹量，各 2 字节 |
| `0x0A04` | 8 | 剩余金币 2 字节、累计金币 2 字节、场地交互状态位图 4 字节 |
| `0x0A05` | 41 | 对方 1/2/3/4/7 号增益、哨兵姿态与各机器人主要状态 |
| `0x0A06` | 6 | 对方干扰波密钥，各字节为 ASCII 字母或数字 |

`0x0A05` 前 35 字节按 1/2/3/4/7 号各占 7 字节排列：回血增益 1 字节、热量冷却增益 2 字节、防御增益 1 字节、负防御增益 1 字节、攻击增益 2 字节。偏移 35 为哨兵姿态（1～6，含强化姿态）；偏移 36～40 为上述五台机器人的主要状态：0=存活、1=战亡、2=无敌但不虚弱、3=无敌且虚弱。

## 2 自定义客户端协议


### 概述

自定义客户端的数据流格式为 **Protobuf v3**（Protocol Buffers，支持 3.15 以上版本），采用 **MQTT** 作为发布/订阅消息传输协议。MQTT 直接传输 Protobuf 序列化的二进制流。topic 为对应的指令名。

- **服务器 IP 地址**：192.168.12.1
- **端口**：3333
- **自定义客户端 IP 地址**：192.168.12.2（固定地址）

### 通信流程

1. 结合文档中的 Protobuf 消息格式编写 `.proto` 文件，用 protoc 生成不同语言的类代码；
2. 在发布者端，将对象序列化成二进制；
3. 通过 MQTT publish 把二进制发送到对应 Topic；
4. 在订阅者端，接收消息并用 Protobuf 反序列化。

> 示例代码见附录三，其中 `MyMqttClient` 的 `clientID` 需填入所连接机器人对应的 ID 编号。

### 图传码流数据

自定义客户端可通过 **UDP 监听 3334 端口** 获取图传码流数据。帧率为 **60 fps**，分辨率为 **1920 × 1080**，编码格式为 **HEVC / H.265**，无重传机制。每个 UDP 包的码流数据前 8 个字节固定为：

- 帧编号（递增）：2 byte
- 当前帧内分片序号：2 byte
- 当前帧总字节数：4 byte

这 8 字节按**大端**传输。每个 UDP 包最大 1400 字节，去掉头部后码流数据最多 1392 字节。

## 2.2 详细协议定义

以下消息定义保留原文的 `optional` 字段声明，创建 `.proto` 文件时需添加 `syntax = "proto3";`。消息名同时作为 MQTT Topic，字段编号、类型和方向应与对应定义一致。

### 2.2.1 KeyboardMouseControl

**用途**：传输鼠标键盘输入。该数据将通过相机图传模块（接收端）发送给机器人。实际比赛时，操作手需提前选择键鼠控制指令来源为官方选手端或自定义客户端，同时仅能通过一个来源生成发送给机器人的键鼠指令。

| 数据编号 | 数据类型 | 数据用途                              |
| -------- | -------- | ------------------------------------- |
| 1        | int32    | 鼠标 x 轴移动速度，负值标识向左移动   |
| 2        | int32    | 鼠标 y 轴移动速度，负值标识向下移动   |
| 3        | int32    | 鼠标滚轮移动速度，负值标识向后滚动    |
| 4        | bool     | 左键是否按下（false=抬起, true=按下） |
| 5        | bool     | 右键是否按下（false=抬起, true=按下） |
| 6        | uint32   | 键盘按键位掩码（bit0~bit15）          |
| 7        | bool     | 中键是否按下（false=抬起, true=按下） |

**键盘按键位掩码**（每个 bit 对应一个按键，0=未按下，1=按下）：

- bit0 : W
- bit1 : S
- bit2 : A
- bit3 : D
- bit4 : Shift
- bit5 : Ctrl
- bit6 : Q
- bit7 : E
- bit8 : R
- bit9 : F
- bit10: G
- bit11: Z
- bit12: X
- bit13: C
- bit14: V
- bit15: B

```protobuf
message KeyboardMouseControl {
    optional int32 mouse_x = 1;
    optional int32 mouse_y = 2;
    optional int32 mouse_z = 3;
    optional bool left_button_down = 4;
    optional bool right_button_down = 5;
    optional uint32 keyboard_value = 6;
    optional bool mid_button_down = 7;
}
```

### 2.2.3 GameStatus

**用途**：同步比赛全局状态信息。

| 数据编号 | 数据类型 | 数据用途                 |
| -------- | -------- | ------------------------ |
| 1        | uint32   | 当前局号（从 1 开始）    |
| 2        | uint32   | 总局数                   |
| 3        | uint32   | 红方得分                 |
| 4        | uint32   | 蓝方得分                 |
| 5        | uint32   | 当前阶段（枚举值见下表） |
| 6        | int32    | 当前阶段剩余时间（秒）   |
| 7        | int32    | 当前阶段已过时间（秒）   |
| 8        | bool     | 是否暂停                 |
| 9 | uint32 | 当局胜者：0=平局，1=红方，2=蓝方；仅结算阶段有意义，其余发送 255 |
| 10 | uint32 | 比赛结束原因；仅结算阶段有意义，其余发送 255 |

**current_stage 枚举值**：

- 0：未开始比赛
- 1：准备阶段
- 2：十五秒裁判系统自检阶段
- 3：五秒倒计时
- 4：比赛中
- 5：比赛结算中

**end_reason 枚举值**：1=基地被摧毁，2=基地剩余血量，3=前哨站剩余血量，4=前哨站是否被击毁过，5=全队总攻击伤害，6=全队机器人总剩余血量，7=平局，8=异常终止，9=主裁判手动判定胜负。

```protobuf
message GameStatus {
    optional uint32 current_round = 1;
    optional uint32 total_rounds = 2;
    optional uint32 red_score = 3;
    optional uint32 blue_score = 4;
    optional uint32 current_stage = 5;
    optional int32 stage_countdown_sec = 6;
    optional int32 stage_elapsed_sec = 7;
    optional bool is_paused = 8;
    optional uint32 game_result = 9;
    optional uint32 end_reason =10;
}
```

### 2.2.7 Event

**用途**：全局事件通知。

| 数据编号 | 数据类型 | 数据用途                         |
| -------- | -------- | -------------------------------- |
| 1        | int32    | 事件编号（枚举值见下）           |
| 2        | string   | 事件参数（含义随 event_id 变化） |

**event_id 枚举值**：

- 1：击杀事件，参数依次为被击杀者、击杀者，如 `1,101` 表示蓝方英雄击毁红方英雄。
- 2：前哨站被摧毁，参数为被击毁的目标 ID，原文 ID 差异见下。
- 3：大能量机关成功激活灯臂数、平均环数，仅大能量机关激活时触发。
- 4：能量机关进入已激活状态，参数 1=小能量机关、2=大能量机关。
- 5：己方英雄造成狙击伤害，参数为累计狙击伤害数量。
- 6：对方英雄造成狙击伤害，参数为累计狙击伤害数量。
- 7：对方呼叫空中支援，无参数。
- 8：对方空中支援被反制，参数为己方剩余可反制次数。
- 9：飞镖命中，参数一为命中方（1=红方、2=蓝方），参数二为目标（1=前哨站、2=基地固定目标、3=基地随机固定目标、4=基地随机移动目标、5=基地末端移动目标）。
- 10：对方飞镖闸门开启，无参数。
- 11：基地遭到攻击，无参数，内置冷却 5 s。
- 12：对方前哨站停转，无参数。
- 13：对方基地护甲展开，无参数。
- 14：装配过程中对方请求四级装配，进入强制退出缓冲期，无参数。
- 15：装配结果，参数值见下。

**V2.0.0 补充**：事件 3 的参数为激活灯臂数和平均环数，例如 `10,9.6`；事件 9 的命中目标还包括 5=基地末端移动目标；事件 15 的结果为 0=成功、1=拔出、2=超时、3=离开装配区过久、4=工程战亡、5=四级协作超时、6=主动退出、7=结算未检测到能量单元、8=强制退出缓冲期到期。原文事件 2 将前哨站 ID 写为 11/111，与附录二的 10/110 不一致，接入时需核对。

```protobuf
message Event {
    optional int32 event_id = 1;
    optional string param = 2;
}
```

## 附录一：CRC 校验

来源：原文第 75～78 页。完整查表数组和 C 示例见文末 PDF 的附录一。

| 校验 | 初值 | 计算范围 | 写入位置 |
| --- | --- | --- | --- |
| CRC8 | `0xFF` | 帧头前 4 字节 | 帧头第 5 字节 |
| CRC16 | `0xFFFF` | 完整帧除最后 2 字节外的全部内容 | 帧尾，低字节在前，高字节在后 |

CRC8 的生成多项式为 `x^8 + x^5 + x^4 + 1`。实现时需与原文的查表运算、初值和收尾方式保持一致；仅选择一个同名 CRC 算法不能保证兼容。

推荐验证顺序：先调用帧头 CRC8 校验，再按 `data_length + 9` 收齐帧并校验 CRC16，通过后解析命令数据。原附录代码中存在类型拼写及全角标点问题，移植时需修正并验证。

## 附录三：自定义客户端示例通信代码

下列示例依赖 Unity、MQTTnet 及项目自己的 `Debugger`、`MqttSubProtoEvent`、`ThreadPool`，并非独立可运行程序。发送协议消息应使用 Protobuf 序列化后的字节数组和对应 Topic。本文将默认地址调整为 `192.168.12.1`，默认 QoS 调整为 `AtLeastOnce`（QoS 1），与第 2 章参数及最高 QoS 一致；原 PDF 示例使用本机地址和 QoS 2，不能直接作为赛场配置。

```csharp
using MQTTnet;
using MQTTnet.Client;
using MQTTnet.Diagnostics;
using MQTTnet.Protocol;
using MQTTnet.Server;
using System;
using System.Collections;
using System.Collections.Generic;
using System.Text;
using System.Threading.Tasks;
using UnityEngine;

/// <summary>
/// MQTT客户端
/// </summary>
public class MyMqttClient {
    private IMqttClient m_MqttClient = null;
    private string m_ClientID;

    /// <summary>
    /// 创建客户端并连接服务器
    /// </summary>
    /// <param name="clientID"></param>
    /// <param name="ip"></param>
    /// <param name="port"></param>
    public MyMqttClient(string clientID, string ip = "192.168.12.1", int port = 3333) {
        m_ClientID = clientID;
        // 客户端选项生成器
        var options = new MqttClientOptionsBuilder()
            .WithClientId(m_ClientID)
            .WithTcpServer(ip, port)
            .Build();
        // 创建客户端
        m_MqttClient = new MqttFactory().CreateMqttClient();
        // 监测客户端连接/断开连接完成
        m_MqttClient.ConnectedAsync += ClientConnected;
        m_MqttClient.DisconnectedAsync += ClientDisConnected;
        // 客户端接收到消息
        m_MqttClient.ApplicationMessageReceivedAsync += ReceiveMsg;
        // 连接服务器
        m_MqttClient.ConnectAsync(options);
    }

    /// <summary>
    /// 接收到消息
    /// </summary>
    private Task ReceiveMsg(MqttApplicationMessageReceivedEventArgs args) {
        Debugger.Log(DEBUGLOGENUM.CustomClient, $"recv topic: {args.ApplicationMessage.Topic}");
        // 消息post出现，以免出现消息堵塞
        MqttSubProtoEvent ev = new MqttSubProtoEvent();
        ev.topic = args.ApplicationMessage.Topic;
        ev.data = args.ApplicationMessage.Payload;
        ThreadPool.CustomClientLoop.PostEvent(ev);
        return Task.CompletedTask;
    }

    /// <summary>
    /// 断开连接完成
    /// </summary>
    private Task ClientDisConnected(MqttClientDisconnectedEventArgs args) {
        return Task.CompletedTask;
    }

    /// <summary>
    /// 连接完成
    /// </summary>
    private Task ClientConnected(MqttClientConnectedEventArgs args) {
        Subscribe("KeyboardMouseControl");
        Subscribe("CustomControl");
        return Task.CompletedTask;
    }

    /// <summary>
    /// 发布消息
    /// </summary>
    public void PublishMsg(string topic, string message, MqttQualityOfServiceLevel level = MqttQualityOfServiceLevel.AtLeastOnce, bool isRetain = false) {
        long unixUs = DateTime.UtcNow.Ticks / 10; // 微秒级
        m_MqttClient.PublishStringAsync(topic, message, level, isRetain);
    }

    /// <summary>
    /// 发布消息（字节数组）
    /// </summary>
    public void PublishBytesMsg(string topic, byte[] message, MqttQualityOfServiceLevel level = MqttQualityOfServiceLevel.AtLeastOnce, bool isRetain = false) {
        long unixUs = DateTime.UtcNow.Ticks / 10; // 微秒级
        m_MqttClient.PublishBinaryAsync(topic, message, level, isRetain);
    }

    /// <summary>
    /// 订阅主题
    /// </summary>
    public void Subscribe(string topic) {
        m_MqttClient.SubscribeAsync(new MqttTopicFilterBuilder().WithTopic(topic).Build());
    }
}
```
