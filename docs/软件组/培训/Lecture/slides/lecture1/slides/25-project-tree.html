工程里都有什么

点击左侧任意文件或目录，右侧查看它的作用。以 STM32F407 + CMake 工程为例。

F407_LED.ioc

需频繁修改

CubeMX 的工程配置文件：芯片型号、每个引脚的功能、时钟树、外设参数全部记录在这里。双击它就能回到 CubeMX 的图形界面。

它是文本文件（XML 格式），但不要手动修改——改配置请通过 CubeMX 界面。建议提交到 Git。

.mxproject

无需处理

CubeMX 的内部记录文件，用来追踪上次生成时的信息。不需要打开，也不需要手动修改。

Core/

主要工作区

装载"与芯片直接打交道"的初始化代码，由 CubeMX 自动生成：Inc/ 放头文件，Src/ 放源文件。

职责很清晰：谁被初始化，就有一个对应的 .c 文件。

Core/Src/main.c

最常打开

程序入口。顺序是：HAL_Init() 初始化 HAL，SystemClock_Config() 配置时钟，然后是各外设初始化，最后进入 while (1) 主循环。

单片机的 main 永不返回，因此没有 return；主循环只处理轻量事务，耗时任务交给 FreeRTOS 任务。

Core/Src/gpio.c、can.c、tim.c …

生成代码，勿手改

每个外设一个文件，里面是 CubeMX 依据你的配置生成的初始化函数：引脚电平与模式、CAN 波特率、定时器分频与 PWM 参数。

想改这些参数，正确做法是回 CubeMX 改配置再重新生成，而不是直接改这里的代码。

Core/Src/stm32f4xx_it.c

谨慎修改

中断服务函数集中在这里，例如 SysTick_Handler、CAN1_RX0_IRQHandler。

原则是中断里只做"搬运数据"，尽快返回；真正的计算交给主循环或 FreeRTOS 任务，否则会阻塞整个系统。

Core/Inc/

偶尔修改

头文件目录：main.h 里有引脚宏定义，gpio.h、can.h 里是各外设的声明，stm32f4xx_hal_conf.h 决定启用哪些 HAL 模块。

想在多个文件里共用自己写的函数，可以在这里加一个自己的头文件。

Drivers/

官方库，勿修改

ST 官方的库文件目录，由 CubeMX 从固件包里拷贝过来：CMSIS 提供内核与芯片定义（stm32f407xx.h 里是所有寄存器的地址）， HAL Driver 提供外设的现成函数。

升级固件包时这些文件会被整体替换，所以永远不要在这里写自己的代码。

Middlewares/

按需生成

中间件目录，只有启用了对应功能才存在：启用 FreeRTOS 后会生成实时内核源码，启用 FATFS 会生成文件系统。

GSRL 就是用 FreeRTOS 做实时任务调度的。

startup_stm32f407xx.s

不要改

启动文件（汇编）：芯片上电后执行的第一段代码。 它设置堆栈指针、初始化数据段、配置中断向量表，最后跳转到 main()。

"程序是怎么跑到 main 的"答案就在这里。文件名中的型号对应你的芯片。

STM32F407ZGTx_FLASH.ld

不要改

链接脚本：告诉 链接器内存怎么划分——Flash 从哪个地址开始、有多大，RAM 在哪里，堆栈放多深。

程序"内存不够"或"跑飞了"，第一个要看的就是它和编译生成的 .map 文件。

CMakeLists.txt

很少改

顶层构建脚本：声明工程名、编译选项、要参与编译的源文件目录、要链接的库。它由 CMake 读取，再生成真正的构建脚本。

自己新增了源文件目录时，需要在这里登记，否则不会被编译进去。

CMakePresets.json

很少改

构建预设：预先定义好 Debug 和 Release 分别怎么构建，VS Code 的 CMake 插件会读取它，让你一键选择配置并编译，不用手敲长命令。

cmake/gcc-arm-none-eabi.cmake

不要改

交叉编译工具链文件：告诉 CMake 用哪个编译器、编译出什么架构的代码——这里是 ARM Cortex-M，而不是你电脑的 x86。

"交叉编译"就是在 PC 上编译、给另一种架构的芯片执行。

build/

产物，不提交

构建产物目录：.elf 含调试信息供烧录与调试，.hex 和 .bin 用来烧录， .map 是地址与空间占用清单。

整个目录都可由源码重新生成，因此不要提交到 Git，删除后重新构建即可。
